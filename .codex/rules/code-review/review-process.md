# Code Review — canonical review-process detail

This file is one of the three that make up the code-review rule set, alongside `@rules/code-review/general.md` (the review's constraints, gates, and output contract) and `@rules/code-review/core-analysis.md` (the catalog of what counts as a finding). A run that applies one applies all three.

The passes below are applied by `@skills/code-review/SKILL.md` (and through it by every CR wrapper). They were extracted from the skill body to keep the skill within the skill-check token budget; the skill references each section by name. Apply every step to the PR diff exactly as if it were inline in the review skill.

## Refactoring & Tech Debt (DRY) Analysis — retired

This section used to walk every changed block against `@skills/class-refactoring/SKILL.md` with `MODE=cr` and emit two sections on the published review: `## Refactoring (DRY / tech debt)` for in-scope items and `## Refactoring proposals` for out-of-scope ones. **Neither section is produced any more, and neither lens runs on a CR.** A refactoring entry never blocked a merge, so a reviewer read it round after round and acted on it in none of them; the round it cost is what this package now spends on the assignment instead.

Retired with it, because each existed only to fill one of those two sections: the Livewire / Blade layout-splitting walk, the `->when()` conditional query-composition rewrite, and the entry-point → Action proposals from `@skills/refactor-entry-point-to-action/SKILL.md` with `MODE=cr`.

**What stays, and where it now lands:**

- **Duplication that is a rule violation is still a finding.** *Reuse of existing logic* in `@rules/code-review/core-analysis.md` owns the reuse-first gate at its own severity, and it is unaffected — a parallel implementation of logic the codebase already has is a finding, not a proposal.
- **Both skills stay shipped and stay usable.** `@skills/class-refactoring/SKILL.md` and `@skills/refactor-entry-point-to-action/SKILL.md` are unchanged and run exactly as before when a caller asks for a refactor. Only their automatic, read-only invocation from inside a code review is gone.
- **The three frontend lenses are unaffected.** `frontend-patterns`, `frontend-a11y`, and `design-system` own what is inside a component and keep running; this walk only ever owned where the markup was split.
- **An out-of-scope problem a reviewer genuinely notices is still recorded.** It travels in the reviewer's handoff and, when it clears the filing bar, becomes its own tracker issue (`@rules/compound-engineering/general.md` *File deferred points as follow-up tracker issues* → *The filing bar*). It just no longer has a section of its own on the PR comment.

**What is lost, stated rather than hidden:** a tech-debt observation that is not a rule violation, not security-relevant, and not worth a tracker issue is no longer written down anywhere a reader of the PR will see. That is the intended trade — those are exactly the entries the round count was being spent on.

## Validation & Coverage Gate

**Ordering — the acceptance criteria are walked first.** `@skills/code-review/SKILL.md` *Acceptance-Criteria Gate (mandatory, runs first)* runs the acceptance-criteria walk ahead of every other analysis step and anchors the review's verdict on it. This section is unchanged by that ordering and stays the canonical contract for **what** the walk checks; the skill owns **when** it runs. When the assignment enumerates no explicit criteria, that gate falls back to the Assignment Conformance Gate and this section's bullet keeps its existing scope, applied to whatever criteria Issue Context Analysis resolved.

- **Acceptance-criteria use-case coverage (mandatory):** for every acceptance criterion, expected behavior, and sample test scenario extracted under **Issue Context Analysis**, verify that at least one automated test exists whose description and assertions directly target that criterion or scenario. A criterion is covered only when a named test (`it('...')` / `test('...')`) exercises the precise use case — not merely when the changed lines happen to be executed by an unrelated test. Any acceptance criterion without a dedicated use-case test is a **Critical** finding. The **Suggested Fix** names the missing test and the layer it should live at (unit, integration, or feature) per `@rules/code-testing/general.md` *Test Organization*.
Do not duplicate the **Coverage gate** finding for the same uncovered line — this bullet owns missing-use-case findings; the Coverage gate owns uncovered lines more broadly.
  - **The test must also use the data the assignment states (issue #69).** Targeting the right scenario with an invented value is not coverage. A reporter who wrote *"an order below 499 Kč is rejected"* and attached the payload named the input that reproduces the defect, and a test asserting the same rejection at 100 Kč never exercises that boundary. A criterion is covered only when a test targets the scenario **and** uses the data the assignment states. **Data** here is anything the assignment fixes concretely: a concrete input value, a request / event payload, a boundary value, an expected output, or an expected error message.
  - **No stated data, no condition.** When the assignment describes the behaviour in words only and fixes no concrete value, this condition does not apply and the bullet keeps its scenario-only standard unchanged. Never invent a value the assignment does not carry and then flag a test for missing it. On a PR whose assignment states no concrete data, this condition raises nothing and the finding counts are identical to what they were before it existed.
  - **What is a deviation (the finding).** A test that bypasses a value the assignment states: a different input value where the assignment fixed one, a payload of a different shape than the one the assignment carries, or a boundary value the assignment names that no test exercises. Raise it as the same **Critical** finding this bullet already owns, one per bypassed datum.
  - **What is not a deviation.** The stated data are a **minimum, never a ceiling**, so none of the following is a finding: the value reaching the assertion through a **named fixture, constant, dataset, or factory** instead of a literal; an **equivalent representation** of the same value (`499` / `499.00` / `'499'`, a `Money` object for a stated amount, a date object for a stated date); or **additional** values, cases, or assertions the test adds beyond the stated ones. Resolve a fixture or constant to the value it holds and judge that value — never the spelling at the call site. A rule that flagged a named constant would fire on almost every well-written test and would be ignored within a week.
  - **The finding carries the data, not a description of it.** The **Test Hint** field names the concrete values verbatim from the assignment — the amount, the payload, the boundary, the expected message — so `@skills/process-code-review/SKILL.md` and `@skills/create-missing-tests-in-pr/SKILL.md` write the test from the finding without re-reading the tracker. A Test Hint that says *"use the value from the issue"* does not satisfy this contract.
  - **Criteria and data come from whichever source Issue Context Analysis resolved** — the linked tracker item, or, on a run with no tracker, the assignment the run itself carries (`@skills/code-review/SKILL.md` *Issue Context Analysis*). The gate is skipped only when no assignment exists in any of those sources, and the review then states that skip as an assumption per `@rules/code-review/general.md` *Safety*.
  - **Gating — one finding per violation, never two.** This condition belongs to this bullet alone. The **Coverage gate** below owns uncovered added / changed lines: a line a wrong-data test executes is covered for that gate, so it never raises a second finding for the same test. **Test organization** (`@rules/code-review/core-analysis.md`) owns the test's placement, file name, description, and AAA order: a test whose description matches its assertions but whose data bypass the assignment is this bullet's finding, never that one's. Never raise two of these three on the same test.
- **Coverage gate (mandatory, scoped to changed files only):** every line, branch, and condition added or modified in the current PR diff must be covered by tests. Verify the coverage of the changed files only — do not gate code review on a project-wide coverage percentage.
  - **Reuse CI results when available.** Before running any local checker, inspect the `statusCheckRollup[]` loaded from the PR JSON (available via the wrapper scripts) and — when needed — fetch the run log via `gh run view` to identify which checks already ran on the **exact PR head commit** (confirm that run's **actually-checked-out SHA** matches the PR `headRefOid`). For every check that is **green on the head commit**, reuse that result directly — do not re-execute it locally. Run locally **only the checks that are missing from CI** (not present in `statusCheckRollup[]`, or present but not yet started / still in progress). The most common case:
CI runs the full test suite but does not publish a changed-files coverage report scoped to the PR diff — in that case run only the coverage tooling (not the full suite) to produce the scoped report. **Staleness guard:** CI results are valid only when that run's actually-checked-out SHA (not merely the workflow's nominal trigger SHA — a `pull_request` event may check out a merge ref) matches the current PR `headRefOid`. When the diff has changed since the last CI run (SHA mismatch, CI not yet triggered, or CI still in progress), treat the prior results as stale and run the relevant checks locally.
**Failing / incomplete CI:** when a check shows `FAILURE` / `ERROR` / missing / `IN_PROGRESS` on the head commit, run it locally (or note it as a finding) — never treat a non-green status as a pass.
  - Use the coverage tooling the project already provides. Discover the available coverage command (a Phing coverage target, a Composer `test:coverage` / `coverage` script, or a direct `vendor/bin/pest --coverage-clover=<file>` / PHPUnit `--coverage-clover` invocation) and run it to produce a coverage report. Do not assume a default and do not add a new bespoke coverage script to the consuming project.
  - Restrict the assessment to the changed source files. When the runner can limit the report to specific paths (`--coverage-clover` plus a path filter, PCOV `pcov.directory` scoped to the changed directories), narrow it so the run stays fast; otherwise generate the report and read off only the changed files.
  - Map the report to the diff and list any uncovered added/changed lines as **Critical** findings.
  - Delete the generated coverage report file (the `--coverage-clover` output or any other auto-generated coverage artifact) as soon as it has been read, so it is never accidentally committed. Keep such artifacts in the project's `.gitignore` as a second line of defence.
  - If the project ships no coverage tooling at all, or it cannot be executed (missing driver, missing test binary, no source directory), raise that as a **Critical** finding instead of skipping the check.
  - **Sanctioned exception — savings-mode isolated-worktree deferral.** A CR pass running in the optional isolated read-only worktree (`agents/athena.md` *Review worktree*) has no installed `vendor/` and cannot execute the coverage tooling at all — when the shared brief records `## Savings mode: on` (`@rules/compound-engineering/orchestration.md` *Savings mode* mechanism 3), this specific, narrowly-scoped case reports the gate as `deferred to hephaestus` instead of the Critical finding the bullet above otherwise requires; the `hephaestus` scoped-validation handoff then carries the mandatory executed verdict. No other reason to skip or fail to execute the coverage tooling qualifies for this exception.
  - **Coverage reporting is short by default.** Run the gate on every review, but render the `## Coverage` section on the published comment **only** when there is something the reader must act on — uncovered changed lines (Critical findings) or unavailable / non-runnable coverage tooling (Critical finding with the reason). When every changed line is at 100% coverage and the tool ran successfully, **omit the `## Coverage` section entirely, omit the `Coverage:` header line, and omit the `coverage …` slot from the final summary line.** The Counts line carries the clean signal; the omission is the report. Never emit `100%` / `clean` / `n/a` placeholders for the section, the header line, or the summary slot.
- Identify missing test scenarios beyond raw coverage (edge cases, error paths, regressions).

## Critical Findings Verification (issue #537) — procedure

Run this step **after every preceding analysis step has produced its findings** (Core Analysis, Highest-Priority Fast Track, Named Arguments Review, Specialized Reviews, Refactoring & Tech Debt, Validation incl. the Coverage gate) and **before** the Output assembly. Walk every **Critical** finding aggregated within this skill's run through `@skills/analyze-problem/SKILL.md` to confirm the finding reflects a real problem in the diff before it blocks the PR.

1. For each Critical finding, invoke `@skills/analyze-problem/SKILL.md` **inline in this skill's context** (do not dispatch as a subagent) and pass:
   - the finding's `file:line`, **risk/impact** line, **Faulty Example**, **Expected Behavior**, **Test Hint**, and **Suggested Fix**
   - the surrounding code context — at minimum the enclosing method / class, plus any helper / Service / Repository the **Suggested Fix** points at — so the analysis can separate facts from assumptions
   - the issue context already loaded under **Issue Context Analysis** (requirements, acceptance criteria, test data, edge cases)
2. Read the returned analysis (template at `@skills/analyze-problem/templates/analysis-report.md`):
   - **Verified Facts** must support the finding's claim
   - **Probable Root Cause** must align with the finding's risk / impact
3. Outcome — binary, no middle ground:
   - **Confirmed** — Verified Facts and Probable Root Cause back the finding → keep the Critical finding verbatim in the report (reproducer fields, severity, and Suggested Fix unchanged)
   - **Refuted** — Verified Facts contradict the finding, or Probable Root Cause names a different cause whose mitigation already exists in the diff → drop the finding from the report entirely
4. **Never silently downgrade** a Critical to Moderate or Minor on the basis of this verification — the gate is binary (kept or dropped). A finding that survives stays Critical; a finding that is refuted is removed. Use the default severity stratification in `@rules/code-review/general.md` *Default severity for a rule violation* (not this verification) for any genuine severity reassessment.
5. **Moderate and Minor findings are not subject to this verification** — they pass through to Output assembly unchanged. The verification exists to eliminate false-positive Critical blockers, not to second-guess lower-severity items.
6. The verification runs on every CR run; the published comment carries only **verified** Critical findings, so reviewers never spend time on a Critical that the analysis itself could not stand up.

## Remediation-conformance ownership — derive once per effective PR diff, not once per reviewer (issue #174)

When a pre-implementation analysis produced findings that the implementation was supposed to remediate — `athena`'s security-risk analysis, an `analyze-problem` plan artifact, or any plan the shared brief carries — **verifying that each of those findings was actually addressed in the diff is a distinct piece of work from hunting new findings.** Nothing previously said who owns it, so in the parallel two-reviewer round this roster used to run, both reviewers did it: measured on the run behind #172, every pass independently re-read the same guard, the same architecture tests, the same disk config, and the same prune command over the same six findings, and reached an **identical** verdict.
The differentiated value of the second derivation was zero; the new findings each pass contributed came from its own lens, not from re-deriving that table. Collapsing the review into a single pass (issue #179) removed the duplication at its source, so on this roster the rule below has exactly one candidate owner — it still matters, because it is keyed to the effective PR diff fingerprint rather than a commit SHA. A history-only rebase therefore preserves it, while changed content re-derives it; a project that does run parallel reviewers still needs the ownership assignment.

- **Exactly one reviewer derives the remediation-conformance verdict per effective PR diff fingerprint.** Where two or more reviewers run in parallel, the owner is the reviewer whose lens produced the plan. **On a single-reviewer roster there is only one candidate** — on this package's roster that is **`athena`** (issue #179), and it owns the verdict whenever a plan exists at all: its own security-risk analysis, an `analyze-problem` plan artifact, or any plan the shared brief carries; with no plan there is nothing to verify and the step is empty, and the *non-owner* clauses below have nobody to apply to. Either way the dispatcher states in the dispatch prompt whether a plan exists, because it is the one that knows whether the pre-implementation analysis step ran.
- **The non-owner does not re-derive it.** It spends its budget on its own lens instead. This removes a duplicate *derivation*, never a check: the verdict is still produced, once, by the reviewer best placed to produce it, and it still lands in the published review.
- **The owner records the verdict where the peer can read it** — one line per plan finding (`addressed` / `not addressed` / `partially addressed`, with the `file:line` that settles it) in its handoff and in the shared brief. A `not addressed` or `partially addressed` entry is a finding at the severity the original analysis assigned it, and it blocks convergence exactly as it would have before.
- **Doubt is a licence to re-verify one entry, not the whole table.** The non-owner may re-check a specific entry when it has a concrete reason to doubt it — the entry contradicts what it read in the diff, or the cited `file:line` does not support the verdict. It then records the divergence, which *Severity divergence between parallel reviewers* below resolves. This keeps the single-derivation saving while preserving the second pair of eyes exactly where a wrong verdict would otherwise go unchallenged; blanket re-derivation "to be safe" is what this section exists to stop.
- **An absent verdict falls back to the non-owner, it never silently disappears.** The consolidating reviewer checks that the owner's verdict is actually present in the brief before publishing. When it is missing — the owner returned `Blocked`, its dispatch failed, or its handoff never landed (this project has already recorded that a background CR dispatch reporting completion is not proof it published) — the non-owner derives the verdict itself for this diff fingerprint and records that it did so. Without this, removing the second derivation turns a redundant check into a single point of failure: a published review would report a converged gate over a verdict no reviewer produced.
- **Keyed to the effective PR diff fingerprint.** A verdict is stale when reviewable content changes, not merely when a commit SHA changes. Never carry it across a different fingerprint; do carry it across a history-only rebase whose fingerprint remains identical.

## Severity divergence between parallel reviewers (issue #172)

When two reviewers run in parallel over the same diff, they can classify **the same defect at different severities**. This roster no longer dispatches such a pair — `athena` is the single CR agent since issue #179, so the divergence cannot arise here — but the contract stays for any project that does run parallel reviewers. Measured: one missing Docker volume, which would have left a prune command unable to see the files it exists to delete, was `Critical` to `argos` and `Moderate` to `athena`; both published, and one had to name the divergence in an addendum.
The convergence gate never read a Minor count, so a *count* disagreement never blocked anything here — but nothing said which severity the merged review carries, and a disagreement across the blocking / non-blocking boundary (`Moderate` vs `Minor`) would leave it genuinely undefined whether the run converges.

- **The higher severity wins.** When the consolidating reviewer merges a peer's findings and both classified the same defect, the merged review carries the **higher** of the two severities. The gate exists to be conservative: a defect one reviewer thought blocking is not made non-blocking by another reviewer's lower read of it.
- **One finding, not two.** The merged review reports the defect **once**, at the winning severity — never the same defect twice under two headings, which double-counts it in the `Counts` line and in the gate.
- **State the divergence in both handoffs.** Each reviewer that classified the defect records its own severity in its handoff, and the consolidating reviewer records the resolution (`severity divergence: <defect> — <reviewer-a> <X>, <reviewer-b> <Y> → published as <X∨Y>`). Recording it in one place only lets the disagreement disappear the moment the losing handoff is skimmed; recording it in both makes the resolution auditable without re-deriving who thought what.
- **A rule-declared severity is not subject to the tie-break.** When one reviewer's severity is the one a rule file's *CR Severity Rules* subsection declares for that violation, that declared severity is what the merged review publishes — the divergence is then one reviewer misapplying the rule, not a judgment split to average upward. Higher-wins governs only the case where both severities are genuine judgment calls with no declared value, which keeps this section from overriding the *Default severity for rule violations* precedence in `@skills/code-review/SKILL.md`.
- **The tie-break is not a substitute for the underlying disagreement.** When the two severities differ because the reviewers read the *defect itself* differently — not merely its blast radius — the resolution belongs in the finding body as one sentence of reasoning, so the author sees why it is blocking rather than only that it is.

## Output Rules — Truthful reporting (issue #74)

Every statement the published review makes must be something the run actually verified — never a plausible guess presented as fact. The review is the input to a merge decision, so a confident-but-wrong line is worse than an omitted one: it authorizes a merge the evidence does not support. This governs the **whole** output, not only the `## Findings` section.

- **Findings state only what was reproduced.** Every Critical / Moderate finding carries the reproducer fields (Faulty Example / Expected Behavior / Test Hint) and survives the *Verified functional-bug analysis* pass — a finding the run cannot back with a concrete failing path is downgraded to a clearly-labelled *possible* observation or dropped, never published as a confirmed defect. "This could break" is not a finding; "this breaks on input X, here is the path" is.
- **Counts are the real counts.** The `Status` and `Counts` line reflect the findings that actually survived verification for **this** head commit — never a carried-over number, never a round figure, never a count that includes a finding the run could not substantiate.
- **A check is reported as run only when it ran.** Never state or imply that a pass happened when it did not. A delegated pass (e.g. `security: owned by athena`) records a **delegation, not a delivery** — it may only be published alongside a link to the delegate's actual, current output, and the merge gate verifies that output exists (`@skills/merge-github-pr/SKILL.md`). A pass that was skipped, errored, or died mid-run is reported as **not done**, never silently omitted so the reader assumes coverage.
- **Uncertainty is labelled, not laundered.** When context is incomplete, state the assumption and what would confirm it (`@rules/code-review/general.md` *If context is incomplete, state assumptions instead of guessing*) rather than resolving the gap with a guess that reads as fact. A claim the run inferred but did not check says so.
- **No fabricated specifics.** Do not invent a `file:line` you did not open, a test result you did not observe, a coverage figure the tool did not emit, or a citation to a rule section you did not read. Every anchor in the report must resolve to something real.

Severity of a violation of this rule (a review that publishes an unverified claim as fact): treat the review itself as non-converged — it must be corrected and re-published before the merge gate may consume it.

## Output Rules — Security & Translation Walks

- **Safe validation & error texts (issue #540):** for every user-facing string the diff adds or modifies — `FormRequest::messages()` / `attributes()`, custom validation messages on rules, exception messages surfaced to end users (`abort()`, `throw new RuntimeException(...)` reaching a JSON / Inertia / Blade response), Notification subject and body, Mailable bodies, flash messages, API error envelopes, Filament notifications, `__()` / `trans()` / `Lang::get()` / `@lang` / `t()` / `i18next.t()` calls **in every locale shipped by the project** (every key under `lang/` / `resources/lang/` / `translations/` / `*.json` locale files), and every literal string rendered into Blade / Livewire / Filament / Vue / React templates —
walk each string against `@rules/security/backend.md` *Safe Validation & Error Messages* and (for frontend / mobile surfaces) `@rules/security/frontend.md` / `@rules/security/mobile.md` *Safe Validation & Error Messages*, and raise one finding per match against any of these patterns:
    - **Identity / account enumeration on auth, password-reset, sign-up, change-email, or account-lookup flows** — distinct wording for *email not found* vs *wrong password* vs *account locked* vs *email not verified* vs *2FA required* vs *user disabled*, or a different response shape / status / latency between those branches.
    - **Authorization granularity leak** — *"You do not have permission to access invoice #42"*, *"Project not found in your workspace"*, or any wording that confirms a resource exists to a caller who is not authorized to read it (the generic `404 Not Found` envelope must cover both *missing* and *forbidden*).
    - **Internal implementation detail in the response body** — stack traces, fully-qualified class names, file paths, framework / library versions, database table or column or index names, raw SQL fragments, ORM error envelopes, queue / cache driver identifiers, feature-flag keys.
    - **Verbatim echo of attacker input** — string interpolation of the rejected value (`"Email '$email' is invalid"`) into the validation message or error body; the rule is to reference the field by name only.
    - **Password / token policy leak beyond the stated rule** — proximity hints (*"one character short"*, *"almost matches the breach list"*), missing-character-class enumeration when several classes are missing, or password-fragment echo.
    - **Translation drift** — the default-locale key carries the safe wording but a translated locale reintroduces an enumeration / authorization / introspection leak (e.g. `en.json` says *"Invalid credentials."* but `cs.json` says *"Účet neexistuje."*). Walk every locale shipped by the project, not just the default. This is **independent of** the Translation completeness check — the wording finding fires even when the key is present in every locale.
    Severity: **Critical** when the unsafe wording sits on an auth / password-reset / sign-up / authorization surface (the leak is directly exploitable for enumeration); **Moderate** on every other user-facing surface. The **Suggested Fix** rewrites the string to a generic, non-enumerating equivalent — *"Invalid credentials."*, *"If the account exists, we sent the reset link."*, *"The email address is invalid."* — routed through the project's translation function in **every shipped locale** (any locale the agent cannot translate confidently keeps the `TODO(<locale>): translate "<source>"` placeholder used by the Translation completeness check above).
Specific, non-enumerating validation messages — *"The age must be at least 18."*, *"Phone number is required."*, *"File must be a PDF under 5 MB."* — are not findings; the gate fires on enumeration / authorization / introspection wording only.
- **Malicious code & supply-chain indicators (issue #549):** walk every line the diff adds or modifies in application code, shell / deploy / CI scripts, `composer.json` / `package.json` script hooks, and installer hooks against `@rules/security/backend.md` *Malicious Code & Supply-Chain Indicators* (and the `@rules/security/frontend.md` / `@rules/security/mobile.md` mirrors for client surfaces), and raise one finding per match against any of these patterns:
    - **Silent remote fetch** — `curl -s` / `wget -q` fetching a payload, especially piped to an interpreter (`curl … | sh` / `| bash` / `| php`) or written to disk and executed.
    - **Disabled TLS validation** — `curl -k` / `--insecure`, `wget --no-check-certificate`, `CURLOPT_SSL_VERIFYPEER => false` / `CURLOPT_SSL_VERIFYHOST => 0`, Guzzle `'verify' => false`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, or a trust-all certificate / hostname verifier.
    - **Suppressed error output** — `2>/dev/null` / `&>/dev/null` on a security-relevant command, the PHP `@` operator on a security-relevant call, `error_reporting(0)`, or an empty `catch {}` that swallows the exception.
    - **Hidden file + detached background process** — a write to `/tmp` / `/var/tmp` / `/dev/shm` or a dot-prefixed filename combined with a detached / backgrounded process (`&`, `nohup … &`, `setsid`, `disown`, `at` / `cron`, detached `proc_open`).
    Severity: **Critical** when the indicator maps to active RCE / MITM / persistence (silent fetch piped to a shell, TLS disabled on a credential-bearing request, both halves of the dropper pattern co-occurring); **Moderate** otherwise. The **Suggested Fix** replaces the unsafe construct with the allow-listed / checksum-verified / logged / queued equivalent from the rule. Documented benign uses (a `-s` curl in a doc example, a `2>/dev/null` on a best-effort cleanup annotated inline) are not findings.
    **Scope boundary — this walk owns the fetch, the trust, and the concealment; the container lens owns the image.** When the container lens `@skills/docker-patterns/SKILL.md` with `MODE=cr` runs over the same diff (`@skills/code-review/references/specialized-reviews.md` *Specialized Reviews*), stage layout and layer caching, pinned base image tags, the non-root user and dropped capabilities, healthchecks, one process per container, and how a secret is delivered to the build (a runtime injection or a BuildKit `--mount=type=secret` against an `ENV` / `COPY` that persists in a layer) are that lens's findings and are never repeated in this walk — raise one finding per violation, never two for the same line.
    The two divide the *dimensions* of a container change, never its lines: one `RUN` line that both disables TLS and installs build tooling into the runtime stage carries one walk finding and one lens finding, because those are two different defects.
    A **hardcoded** secret in any of those files stays with `@rules/security/backend.md` *General Secure Coding Practices*, never with the lens.
- **Malicious file upload content (issue #680):** when the diff touches any upload sink (file-accept, store, process, or serve endpoint), any code that renders a filename, file metadata, or file content into a UI, or any CSV / XLSX / SVG / HTML export or import path — walk the added / modified lines against `@rules/security/backend.md` *Malicious File Upload Content* (and the `@rules/security/frontend.md` / `@rules/security/mobile.md` mirrors for client surfaces), and raise one finding per match against any of these patterns:
    - **Stored XSS from file content** — raw file bytes rendered as HTML, user upload served without `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, or file content injected into a template without escaping.
    - **SVG with active content served inline** — user-uploaded SVG embedded as inline HTML, via `<embed>` / `<object>`, or via `innerHTML`; SVG served with no sanitization of `<script>`, `on*` attributes, or `<foreignObject>`.
    - **CSV / Excel formula injection** — user-controlled cell values written to CSV / XLSX / ODS without an apostrophe-prefix guard against leading `=`, `+`, `-`, `@`, `\t`, or `\r`.
    - **HTML / JavaScript in filenames or metadata** — filename, EXIF field, or PDF metadata rendered into HTML without HTML-encoding; filename interpolated raw into a `Content-Disposition` header, a log line, or a path without sanitization.
    - **Polyglot files served from application origin** — user uploads served from the same origin as the application without `X-Content-Type-Options: nosniff` and a strict CSP, making polyglot execution possible.
    - **Missing `Content-Disposition` / `nosniff` on upload-serving endpoint** — upload endpoint omits `Content-Disposition: attachment` (or a validated, narrowed `Content-Type` for inline previews) or `X-Content-Type-Options: nosniff`.
    > **Scope boundary — CONTENT / RENDER only.** This rule covers the CONTENT / RENDER surface of an uploaded file (active content executed when the file's bytes, name, or metadata are later rendered or served). The file TYPE / TRANSPORT surface (extension allow-list, declared-vs-actual MIME, magic-byte signature, double extension, path traversal, executability in webroot) stays with `security-review/SKILL.md` File Handling — **raise one finding per violation, never both**. A single upload sink that fails both surfaces produces the type/transport finding for the accept decision and the content/render finding for the output decision, on distinct lines; never two findings for the same line.
    Severity: **Critical** for stored XSS (SVG inline, HTML upload served as `text/html`, polyglot on app origin) reachable by other users; **Moderate** for CSV formula injection, unescaped filename / metadata in HTML, missing `nosniff` / `Content-Disposition`.
- **Translation completeness (mandatory when the project ships translations):** detect whether the project uses translations by looking for any of: a `lang/` directory (Laravel), a `resources/lang/` directory (older Laravel layout), a `translations/` directory (Symfony), `*.json` / `*.po` / `*.mo` locale files under a recognised locale directory, calls to `__()` / `trans()` / `Lang::get()` / `@lang` / `t()` / `i18next.t()` / `useTranslation()` / `$t(` / `$tc(` anywhere in the diff or in the wider project.
**If none of those signals match, skip this section entirely.** When translations are in use, for every user-facing string introduced or modified by the diff — across all three surfaces named in `@rules/laravel/laravel.md` **Localization and Translatable Strings**:
**UI** (labels in Blade / Livewire / Filament / Vue / React templates, validation messages, Notification subject and body, Mailable / Markdown views, FormRequest custom `messages()`, enum `getLabel()`, Filament resource / form field labels), **Console** (human-readable Artisan command output — `$this->info()` / `error()` / `warn()` / `line()` / `comment()`, `ask()` / `confirm()` / `choice()` prompts, table headers), and **API** (JSON `message` fields, `abort()` / `abort_if()` descriptions, human-readable strings in API Resources, exception messages surfaced to users), plus log messages exposed to humans — walk every detected locale and raise one finding per missing key —
that is, the diff added a translation key in the default locale but did not add (or updated but did not synchronise) the same key in every other locale shipped with the project, **or** the diff hard-codes a literal string in a user-facing surface even though the surrounding code uses `__()` / `t()` for analogous strings. Severity: **Moderate**; escalate to **Critical** when the missing key is on a primary-flow surface (login, checkout, primary CRUD form, transactional email) or when the project's CI / build asserts translation parity and the diff would break that gate. Each finding cites the missing locale and key, and the **Suggested Fix** is the literal translation entry the locale file is missing (translated into the locale's language;
for languages the agent cannot translate confidently, leave the value as `TODO(<locale>): translate "<source>"` and flag the gap explicitly so a human translator picks it up).

- **Referenced translation key must exist (issue #37):** independently of the completeness walk above — which owns a key present in the default locale but missing from another — for every translation call the diff **adds or modifies** (`__()`, `trans()`, `trans_choice()`, `Lang::get()`, `@lang`, `t()`, `$t(`, `i18next.t()`) resolve the key against the project's locale files and raise one finding per key that exists in **no** locale at all. Laravel does not fail on a missing key:
`__('user.profile.saved')` returns the literal string `user.profile.saved`, which is then rendered to the user as if it were a sentence. The failure is invisible to every other gate — the code compiles, the completeness walk sees nothing added, and the hard-coded-literal walk sees a correct `__()` call — so a dotted identifier reaches production and is shown to a real user. Resolve both key layouts: dotted keys against `lang/{locale}/{file}.php` (`user.profile.saved` → file `lang/en/user.php`, key `profile.saved`) and full-sentence keys against `lang/{locale}.json`. A key assembled at runtime (`__('status.' . $order->status)`) cannot be resolved statically — do **not** guess:
raise it only when **no** key matching the static prefix exists in any locale, and state in the finding that the key is built dynamically. Severity: **Moderate**; escalate to **Critical** on a primary-flow surface (login, checkout, primary CRUD form, transactional email), where the raw key is visible to every user of that flow. The **Suggested Fix** is the missing entry added to **every** shipped locale, in the same form the completeness walk uses (`TODO(<locale>): translate "<source>"` for locales the agent cannot translate confidently). **Scope boundary:** the completeness walk owns a key that exists in the default locale but is missing from another; this walk owns a key that exists nowhere. Raise one finding per key — never both.
- **Test isolation — no real HTTP, no real system processes (mandatory on every test file in the diff):** for every test file added or modified by the diff (any `*.php` under the project's test root — `tests/`, `*Test.php`, Pest `it()` / `test()` files), scan for code paths that can reach the real network or spawn a real OS process, per `@rules/laravel/laravel.md` **Testing**. Two independent gates, both **Critical** (a test that escapes its sandbox is non-deterministic and a security risk — it can hit production endpoints, leak credentials, or execute arbitrary host commands during CI):
    - **Real outbound HTTP** — the test exercises an outbound HTTP integration (Laravel `Http::` client, Guzzle, cURL, `file_get_contents()` against a URL, a vendor SDK that calls out) **without** a registered fake/mock: no `Http::fake()` (or `Http::preventStrayRequests()`), no Guzzle `MockHandler`, no injected fake client. A test that can reach a real endpoint is the finding even when the call happens to be stubbed at the assertion layer but the transport is still live.
    - **Real system process / external binary or script** — the test reaches a real OS process via `Process::run()` / `Process::start()` (Laravel) **without** `Process::fake()`, `Symfony\Component\Process` actually executing, or any of `exec()`, `shell_exec()`, `system()`, `passthru()`, `proc_open()`, `popen()`, or backtick operators running a host command. **A test must never invoke an external binary or script directly on the system** — calling out to `git`, `node`, `npm`, `composer`, `ffmpeg`, `docker`, `aws`, a `.sh` / `.py` / `.bin` script, or any other host executable through a test is a finding on the spot;
the process layer **must be mocked / faked** (`Process::fake([...])`) so the test asserts the intended command line without ever executing it. The only non-finding is the project's own Artisan command driven through `Artisan::call()` / `$this->artisan()`; every external binary or shell command is flagged.
    For each match cite `file:line`, name which gate fired, and give a **Suggested Fix** that registers the missing fake (`Http::fake([...])` / `Process::fake([...])`) or injects a test double so the test asserts the intended request / command without executing it. Documented, explicitly-isolated integration tests that the project marks as such (a dedicated `tests/Integration` group gated behind an env flag / CI stage and annotated in code) are exempt — cite the annotation in the finding instead of raising it. `Http::fake()` / `Process::fake()` / `Artisan::call()` are the Laravel-specific examples;
on a non-Laravel PHP project apply the same two gates with the framework's equivalent isolation — Guzzle `MockHandler` or an injected fake HTTP client, a Symfony `Process` test double, or any injected double — and phrase the **Suggested Fix** in that project's vocabulary.
