## Concurrency & the working-tree write-lock

This section is the normative contract. `agents/splinter.md` is its one executor today and references it by name; nothing here is restated there.

**Worktrees — the writing path stays on the shared tree; a read-only review may isolate.** **The writing path never uses git worktrees.** The orchestrator never creates one, never requests one, and never instructs `donatello` to run in an isolated worktree. Every writing run — yours and every concurrent `splinter` — operates on the **single shared git working tree** of the project, and there is no isolated-worktree escape for the writing path; concurrent writers serialise on the write-lock below instead.

The **read-only code-review agent (`leonardo`) may use a git worktree** for its review when needed — this is the explicit-request opt-in of `@rules/git/general.md` *Worktrees / Workspaces*, which this workflow grants to the CR pass only. Because the CR agent never writes to the tree, an isolated read-only checkout lets it review a stable diff without contending with the writing path.
A CR worktree is a throwaway review checkout: the agent reads in it and never edits / commits / pushes there, it records the worktree path in its handoff, and **`splinter` removes it during its own *Run cleanup*** (`agents/splinter.md` step 7, where that checklist is written down) so nothing orphaned survives the run — including when the run's own turn ends at the `Blocked` stop in step 6 instead of on convergence, which is the path that would otherwise strand the checkout.

Multiple top-level `splinter` runs can be launched against the **same project at the same time** (interactively). Because the writing path never uses worktrees, every writing run shares **one git working tree**. Two runs that both **write** to that tree corrupt each other: `donatello` checks out a branch, edits files, and may `git stash` / `reset` — pulling the tree out from under another run and colliding on uncommitted edits. A run that only **reads** the tree (analysis-only → `leonardo`, or backlog-only, which touches the tracker and never the tree) is safe to overlap.

The fix is a **scope-conditioned write-lock**: only the writing scope (full-delivery → dispatch `donatello`) takes the lock and serialises; the read-only scopes (analysis-only → `leonardo`, and backlog-only run inline) take nothing and stay parallel. The scope signal already exists — it is the classification the orchestrator makes in its step 3 (`backlog-only` vs `analysis-only` vs `full-delivery`).

- **Keyed to the working-tree toplevel.** The lock lives at `.claude/run/.splinter-write.lock` (a **directory**), inside the same git-ignored `.claude/run/` of the current toplevel as the shared brief. Because the writing path never uses worktrees, every full-delivery run resolves to the **same** toplevel and the **same** lock, so concurrent writing runs always contend on it and **serialise** on the shared tree — there is no isolated-worktree toplevel that a writing run could take to slip past the serialisation (the read-only CR worktree carries no write-lock and never contends here).
- **Atomic acquire.** Create the lock with `mkdir .claude/run/.splinter-write.lock` — `mkdir` is atomic and fails when the directory already exists, so it doubles as a test-and-set. On success, write the holder inside it: `PID` — this run's `$PPID`, **never `$$`** (the ephemeral per-Bash-call subshell PID, dead moments after that one tool invocation returns — the same single PID source the orchestrator's startup sweep uses, so every mechanism agrees) — the run's `source-slug`, and `STARTED`, an ISO-8601 timestamp recorded at the moment of this write.
- **Stale reclaim.** When `mkdir` fails, read the holder's `PID` and probe it with `LC_ALL=C kill -0 "$PID" 2>&1` — force the `C` locale so the failure message is always English; on glibc, `strerror()` is locale-translated, and a translated message would silently drop the `"not permitted"` substring the distinction below depends on. `kill -0` conflates "no such process" (ESRCH — genuinely dead) with "process exists, no permission" (EPERM — alive under another UID/namespace); only a failure whose message does **not** mention "not permitted" is a confirmed-dead probe. If the probe is confirmed-dead, the holder is a dead run, the lock is **stale** — `rm -rf` it and re-acquire.
  If the probe finds the PID alive (success, or a failure mentioning "not permitted"), corroborate identity before trusting it as a live blocker — a bare alive PID only proves that PID number is currently in use by *something*, not that it is the same process that wrote `STARTED` (`write-lock-staleness-needs-corroborating-evidence-not-bare-pid` names exactly this gap for the reclaim path).
  Compute that process's own start time from its elapsed run time — `ps -o etime= -p "$PID"` (portable across macOS/BSD and Linux; parse the `[[dd-]hh:]mm:ss` output into seconds and subtract from the current time) — and require it to fall at or before `STARTED`, allowing a small tolerance (e.g. 60 s) for clock/measurement skew: a process cannot have written a timestamp before it existed. When the computed start time is **after** `STARTED`, the PID has been recycled by an unrelated process since the lock was written — identity is **not corroborated**, so treat the lock exactly like a confirmed-dead probe: `rm -rf` it and re-acquire.
  When `STARTED` is absent from the holder file (an older lock predating this field), or `ps -o etime= -p "$PID"` yields no parseable elapsed time (the process exits between the `kill -0` probe and the `ps` call, `hidepid=2`, a PID namespace), the identity check is **inconclusive, not falsified** — treat the lock as held by a live run and report the inconclusive corroboration, mirroring the fail-safe default the orchestrator's startup sweep applies to a missing or malformed `## PID`; only a *successfully computed* start time **after** `STARTED` justifies reclaiming the lock.
  Only when the alive probe **and** the identity check both hold does a live full-delivery run genuinely hold this working tree: **do not proceed into `donatello`**.
- **Release.** Remove the lock (`rm -rf .claude/run/.splinter-write.lock`) during *Run cleanup* — on the final report **and** on any `Blocked` stop — right next to the existing `rm -f "$BRIEF"`, so no orphan lock survives the run.

Only the full-delivery path acquires and releases the lock. An analysis-only run never touches it, so any number of `leonardo` security-analysis runs overlap freely with each other and with one writing run.

**Sequential processing of multiple sources (no fan-out).** When a **single request resolves to multiple sources** (e.g. "analyse these issues", a batch of links, or several sub-issues), process the sources **one at a time, strictly sequentially — never in parallel**. Finish one source's run completely (analysis-only → its `Security analysis done` handoff lands; full-delivery → its convergence gate is satisfied and the brief cleaned up) **before** starting the next. Do **not** fan work out across sources with multiple `Task` tool uses in one message — neither the read-only analyses nor the full-delivery sources.
Each source still gets its **own** shared brief (`.claude/run/<source-slug>.md`, one per source — the slug is already per-source). Order the sources by the dependency-aware plan from the orchestrator's step 1 when they are interlinked (dependencies before dependents), otherwise oldest-first. Report the batch only after **every** source has finished its run in turn.
