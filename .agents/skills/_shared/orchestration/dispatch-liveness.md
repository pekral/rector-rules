# Liveness check for a long-running dispatch (a round that never comes back)

Extracted from `agents/splinter.md` so the orchestrator does not carry it on every run. **Loading trigger:** a turn resumes while a round is still open in the dispatch ledger — a `dispatched` line with no later `delivered` / `failed` / `skipped` — and ten minutes or more have elapsed since that round's `dispatched` timestamp or its last `liveness` line. A round that delivers its handoff before that gate elapses triggers no check, which is the majority of rounds, and this file is then not read.

### Liveness check for a long-running dispatch (a round that never comes back)

A dispatch that returns a handoff is a step you can act on. A dispatch that returns **nothing at all** — the child hung, died, or was killed — leaves you with no signal whatsoever, and nothing above detects it: *Dispatch blocking* keeps your turn from ending mid-flight, and the *Dispatch ledger* below makes a **re**-dispatch detectable, but neither notices a round that simply never comes back. This section is that missing detector. It is the earlier-stage sibling of `docs/memory/PROJECT_MEMORY.md` → `background-cr-dispatch-can-silently-lose-output`, which covers a dispatch that *finished* and mis-reported its result; here the dispatch never finishes at all.

**The check is a non-intrusive state read, never a question sent into the running agent's context.** Never send an "are you still alive?" / "are you done?" message to a dispatched agent: it lands in that agent's next tool round, spends the context you dispatched it with, and can derail the very task you are checking on — and this harness's own tool guidance says so in as many words (*"Never poll ListAgents in a loop or send 'are you done?' messages instead"*). Two paths exist, and whenever a check comes due at all you name in your final report which of the two this run took — through the conditional **Liveness checks** item of your handoff contract (*Output — handoff to the user* below), which renders on exactly those runs:

1. **A non-intrusive state-read primitive is available.** Use it, and only it: `ListAgents` (per-agent `busy` / `idle` status, which costs the running agent nothing to read), or a `SendMessage` carrying `notify_when_idle: true` **and no `message` body** — a pure subscription that notifies you once when the agent goes idle, writing nothing into its context.
2. **No such primitive is available — today's default on this roster, not a hypothetical.** Your own tool list is `Task, Read, Glob, Grep, Bash`: it enumerates neither `ListAgents` nor `SendMessage`, so unless the harness exposes such a read to your instance, you **cannot** perform a genuine mid-flight liveness read at all, and the harness's own automatic completion notification is the only signal you have. State that limitation plainly in your reasoning and in the same **Liveness checks** report item, exactly as you would any other environment limitation.
**Never fabricate the check**: never report a liveness read you did not perform, and never substitute a Bash probe for one — a dispatched subagent is not a process whose PID you hold, while every `kill -0` / `ps` probe your *Bash boundary* permits targets a PID this run's own state files record: a write-lock or sweep-lock holder, a stale brief's `## PID` line, a locked CR worktree. None of those is a dispatched child.

This is a different question from the confirmed-dead PID probe in step 2 and in ***Run cleanup***. That probe asks whether a **process** is dead so its worktree may be removed; this one asks whether an **open round** is still making progress. Never substitute one for the other.

**"Every 10 minutes" is an elapsed-time gate, not a timer.** You hold no sleep or timer primitive — foreground `sleep` is blocked in this harness — so nothing wakes you on a schedule. Instead, whenever your own turn runs (a dispatch returns, a notification arrives, the user or a coordinator writes to you) while a round is still open in the ledger — a `dispatched` line with no later `delivered` / `failed` / `skipped` — compute the elapsed wall-clock time since the later of that round's `dispatched` timestamp and the last `liveness` line recorded for it. When that elapsed time is **≥ 10 minutes**, perform one check now and record it.
The cadence is therefore approximate by construction: the check lands at roughly the requested interval across a run that keeps waking, and not at all during a stretch in which nothing wakes you. Never describe it to the user as a background timer.

One consequence to state rather than hide: with `run_in_background: false` your turn is suspended for the length of the dispatch, so a strictly blocking round gives you no turn to check in. The check's real surface is a round you find **still open when a turn does resume** — a run resumed after a crash or a kill, a wake-up notification, or a dispatch that returned before its child finished. That is a limit of this mechanism, never a reason to weaken *Dispatch blocking*: blocking dispatch stays the rule.

**What recovers the run when no turn ever resumes at all.** That limit bounds the check, never the run — say what covers the rest, or a reader concludes nothing does. Two of this run's state files outlive the session that wrote them: the brief's `## PID` and the write-lock holder. The **next** `splinter` run started against this tree reads **both** — step 2's startup sweep probes the brief's `## PID`, step 5's write-lock acquire probes the holder — and ends in one of two visible outcomes: it reclaims a **confirmed-dead** holder's artifacts and proceeds, or it stops on one that is **not confirmed dead** with a named `Blocked` (`a live run holds the brief for this slug` in step 2, `another splinter writing run holds this working tree` in step 5).
*Not confirmed dead* is deliberately wider than *live*: an EPERM probe, a missing or malformed `## PID`, and a token that fails the format check all land in it, exactly as the fail-safe default those two steps already prescribe. A human therefore gets a signal either way, never an indefinite silent wait. That outer recovery is the **complement** of this check, never a substitute for it: those probes ask whether a *process* is dead — the confirmed-dead PID probe of step 2 and ***Run cleanup***, which this section already sets apart from the open-round question — and neither of them ever reads whether an open round is making progress.

**Precedence over the ledger's in-flight stop — this check runs first.** *Dispatch ledger* → *Consult it before every dispatch* below governs the very same state, an open round found when a turn resumes, and ends it with `Blocked: round <role>/<round> is already dispatched and delivered no result`. Read literally and in isolation, that stop would fire on every round this check exists to examine, and the mechanism would never run on its only real surface. It does not, because that stop is the ledger's **last resort** for an open round — it applies *"when there is genuinely none [no handoff] and the run cannot continue"* — never its first move.
The order over an open round is therefore fixed: read the handoff when one has landed; otherwise run the liveness check that is due for the round and act on its verdict; only when no check can run at all — path 2 above, no state-read primitive on this instance — does the ledger's stop apply unchanged. The two `Blocked` strings are not two names for one fact: the ledger's names a round that delivered nothing and cannot be examined, and this section's names a round a check examined and found without a sign of life. Neither rule ever re-dispatches the round.

**Record every check in the dispatch ledger**, one line per check, under the same per-brief append lock every other ledger write uses:

```text
<role>|<pr-head-sha or ->|<round>|liveness <n>/6 — <observed state>|<ISO-8601>
```

Never write these lines into `${BRIEF%.md}.audit`. A liveness read contacts no host, writes nothing outside the working tree, and creates nothing externally visible — it is none of the audit trail's event classes (`@rules/compound-engineering/orchestration.md` *Audit trail for memory reads, outbound requests, and external writes*) and it adds no row to that file's *Externally-visible actions & consent levels* inventory.

**Two counters run per round, and they are different numbers.** The **no-progress streak** counts consecutive checks that observed **no** progress signal; a check that does observe progress resets that counter — and only that one — to zero, and it is the only counter that escalates a round. The **check count** is the `<n>` in `liveness <n>/6`: it increments once per check written for the round, is **never reset**, bounds the checking itself, and escalates nothing on its own. Never write "the counter" for either of them.

- **Stuck means three consecutive checks without progress, never one `busy` reading.** A round is a stuck-suspect when it reads `busy` (or any non-idle equivalent) across **3 consecutive liveness checks** and shows **no progress signal** between them — no new ledger line, no new handoff section in the brief, no observable partial output. In other words the no-progress streak reaches 3, which at the ~10-minute gate is roughly **30 minutes of zero externally visible movement**. A single `busy` reading proves nothing: most dispatches run busy for the whole of their legitimate 3–15 minutes. Sustained absence of progress is the signal, never one sample of it.
- **On detection, escalate — never continue silently.** `@rules/compound-engineering/general.md` *Blocked delegation is a hard stop* governs this verbatim: you never finish a stuck delegate's work in your own context. In order: (a) when the harness gives you a way to stop that specific dispatched task, use it, write `failed` for the round, and report; (b) otherwise stop the run with **`Blocked: round <role>/<round> shows no sign of life`**, naming the role, the round, the elapsed time, and the number of checks performed, and recommend that the user inspect or terminate it.
- **Never re-dispatch a stuck round without first confirming the original is dead.** An undead duplicate can double an external write — a second PR, a second published comment — which is the exact failure class the *Dispatch ledger* exists to prevent. An unconfirmed death is a report, never a re-dispatch.
- **Cap the check count at 6 per round** (≈ 60 minutes of elapsed wall-clock at the ~10-minute gate), and write no further liveness line for that round afterwards. An unbounded sequence of checks is itself a way of being stuck. This mirrors the `maxIterations = 3` safety net the CR loop already uses — the cap exists so the checking terminates, not because 6 is a measured threshold.
- **The cap escalates a round without progress, never a round that is moving.** Past the sixth check, treat the round as failed-by-timeout and escalate as `Blocked` **only when it has shown no progress signal since its last progressing check** — a `busy` reading is a state, not progress, so it never counts as one. A round the checks watched **make** progress is never declared `Blocked` for having taken an hour: elapsed time alone is not evidence of being stuck, and escalating on it would imprison visibly moving work behind the no-re-dispatch rule below. Report such a round as progressing but no longer checked, and let *Dispatch blocking* and the ledger govern it from there.
In practice the no-progress streak above reaches 3 first for a genuinely stuck round, so this branch of the cap is the outer safety net rather than the primary detector.
- **When the check does not apply — the majority case.** A round that delivers its handoff before 10 minutes elapse triggers no check at all. This is a safety net for the tail, never a step of the golden path: it never delays a dispatch, never precedes reading a handoff that has already arrived, and never runs against a round the ledger already shows closed.
