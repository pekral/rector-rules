# Clarifying questions — severity gate and already-answered walk

Expanded procedure for the *Clarifying questions block* of `@skills/code-review-jira/SKILL.md` *JIRA (consolidated non-technical comment)*.

- **Severity gate — Critical and Moderate questions only (issue #208).** Classify every candidate question by what its answer changes, and emit only the two top classes:
  - **Critical** — without the answer the change cannot be accepted at all: a missing acceptance criterion the implementation had to guess, a contradiction between the ticket and a comment that points at two incompatible behaviours, or a blocking documentation request from the Third-Party API & Service Analysis step 7.
  - **Moderate** — the change ships either way, but the answer decides whether the behaviour it already implements is the intended one: an undefined edge case the code resolved by picking a default, an unspecified value or limit, an unstated failure mode.
  - **Minor — dropped, never asked.** Wording, naming, formatting, curiosity about intent that changes no behaviour, and anything the reviewer can answer for himself by reading the diff. A question that would not change the implementation or the accept / reject decision is not a clarifying question; it is noise on a ticket a non-developer reads.

  Severity is a property of the **question**, not of any finding it relates to, and it is never rendered — the block carries the surviving questions as plain sentences, in Critical-before-Moderate order, with no severity label, count, or heading per class. JIRA carries no severity vocabulary (see the constraint below).
- **Already-answered walk — never re-ask a question the tracker already answered (issue #208).** A CR run repeats on every iteration, so a question asked in run 1 and answered in a comment would be asked again in run 2, and again in run 3 — the reader sees an unchanged block, assumes nobody read the reply, and stops answering. Before assembling the block, walk **every comment already loaded by step 1** (`load-issue.sh`) and drop each question that is settled:
  - **Sources to walk.** The JIRA issue's own comments and the comments of every subtask in `subtasks[]`, the linked GitHub PR description and its review comments, and the comments of every entry in `closingIssues[]`. Step 1 has already loaded all of these — this walk re-reads that context, it never issues a second fetch. A comment restricted by `visibility` is read like any other; it is an answer to the team even when it is not public.
  - **Drop only on both halves.** A question is dropped when **(a)** a comment answers it — states the missing criterion, names the value, resolves the contradiction, or links the requested documentation — **and (b)** the reviewed diff actually implements that answer. Verify (b) against the code, never against the comment's own claim that it was done.
  - **Answered but not implemented → not a question any more.** When (a) holds and (b) does not, the ticket already decided and the code diverges from that decision. Do not re-ask it here; raise it as a finding on the GitHub PR comment against the answering comment as its source (Critical when the decision was an acceptance criterion, Moderate otherwise), so it lands where findings are fixed instead of where questions are asked.
  - **Ambiguous answers stay questions.** A reply that restates the question, defers it ("we will decide later"), or answers a neighbouring question is not an answer. When it is unclear whether a comment settles the question, keep the question — asking twice costs a reader a moment, dropping a live blocker costs a wrong implementation.
  - **Never cite the answering comment in the block.** A dropped question leaves no trace on the JIRA comment; the audit trail is the chronological comment sequence, which already holds both the question and its answer.
